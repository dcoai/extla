# Conformance corpus

Phase 3's acceptance criterion, and it is a weaker one than Phases 1 and 2 had. That is
worth saying plainly.

The differential corpus (`test/differential/`) is measured: `expected.json` is TLC's own
output, regenerated by CI, and a drift fails the build. There is no TLC for *"does this
GenServer refine this specification"*, so the expected verdicts here are **authored**.

What the corpus still buys is the thing that made `raft_election`'s
`eventually_elect_leader` the row worth having: for every entry there is an
implementation that conforms and a set of deliberately wrong twins, and **each twin must
be caught, and named correctly**. A conformance checker that reports success on
everything agrees with the conforming half of every entry and fails every mutant row.

## Layout

```
test/conformance/<name>/
  spec.ex          the specification, from spec/07-examples.md, verbatim
  refinements.ex   the mapping that conforms, and the mapping mutants
  impl.ex          the GenServer that conforms, and the step mutants
```

Verbatim from `07-examples.md` is deliberate, and the same rule the differential corpus
follows: the corpus checks the documentation rather than a paraphrase of it. If the
example in the docs does not behave the way the docs say, that is the bug worth finding.

## `counter` — the mapping mutants

Each is wrong in exactly one way, and `ExTLA.Refinement.validate!/3` or `abstract!/3` must
say which.

| Mutant | Fault | Caught by | Reported as |
|---|---|---|---|
| `MissingVariable` | maps `count`, forgets `status` | `abstract!/3`, at runtime | `missing: [:status]` |
| `ExtraVariable` | maps a key the spec never declared | `abstract!/3`, at runtime | `extra: [:max]` |
| `NotTotal` | no catch-all `abstract_action/1` clause | `validate!/3`, by probe | "is not total" |
| `PartialHelper` | has the catch-all; the helper it calls is partial | `validate!/3`, by probe | the helper's own `FunctionClauseError`, *not* "is not total" |
| `WrongWayRound` | `concrete_message/2` and `abstract_action/1` do not compose | `validate!/3` | "does not round-trip increment" |
| `ActionNeverNamed` | no message produces `reset` | `validate!/3` | "names no message for [:reset]" |
| `NoClauseForAction` | `concrete_message/2` has no clause for `reset` at all | `validate!/3`, from the clauses `@on_definition` recorded | "has no clause for [:reset]" |
| `NoAbstractAction` | not a refinement mapping at all | `validate!/3` | "does not define abstract_action/1" |

The last one deliberately does not `use ExTLA.Refinement`: with the behaviour declared the
compiler already warns, so what is left to catch is a module handed to `refinement:`
without ever claiming to be one.

## `counter` — the step mutants

Written down before the checker existed, for the reason the TLC oracle landed before the
model checker: an answer with nothing to compare it against is a claim. Each is now
checked by `ExTLA.GenServer.Runtime.check_step!/5` through a running server, in
`step_test.exs`.

| Mutant | Fault | Must be reported as |
|---|---|---|
| `CollapsesTwoSteps` | Example 4's own bug: `increment` leaves `status: :ready`, folding `increment` and `done` into one callback | `:diverged`, naming `status` |
| `MovesWhileUnmapped` | `:get` changes the abstract state | `:unmapped_but_moved` |
| `IgnoresTheGuard` | increments from `status: :incrementing`, which the spec's guard forbids | `:not_enabled` |
| `Conforming` | — | no violation |

All three are caught, and each is named as written. `CollapsesTwoSteps` reports
`:diverged` with the one-variable diff `status: spec :incrementing, implementation
:ready`; `MovesWhileUnmapped` reports `:unmapped_but_moved` with `count: 0 -> 1`;
`IgnoresTheGuard` reports `:not_enabled` on `%{count: 0, status: :incrementing}`. The
second assertion in the `CollapsesTwoSteps` test is the one that matters most: it checks
the spec's invariants against the post-state the mutant produced and they *pass*, which is
what a Layer 3 without a step check would have reported.

`CollapsesTwoSteps` is the entry that justifies the layer. **Every invariant in the spec
still holds in its post-state** — `in_bounds` is satisfied by `count: 1` — so a Layer 3
that checked only invariants and action properties would report conformance. It is the
ordinary bug, not a corner case: an implementation taking a shortcut the design never
sanctioned.

## `counter` — replay

`BuggySpec` is the same counter with a design bug written into it: `increment` runs up to
`max_val` and the invariant says the count never exceeds two. Nothing about the
implementation is wrong — the specification contradicts itself, `mix extla.check` finds it
before any code exists, and `Impl.FaithfulToABuggySpec` refines it exactly. A spec whose
invariant no behaviour violates cannot produce a counterexample, which is why this entry
exists at all.

| Case | Implementation | Verdict |
|---|---|---|
| the model checker's counterexample, replayed | `FaithfulToABuggySpec` | `:violation`, `:invariant`, at the step the trace reaches `count: 3` |
| a trace calling for a message the server has no clause for | `RefusesDone` | `:not_followed` — "permits a behaviour the implementation does not take" |
| a trace whose expected post-state the server does not reach | `Conforming` | `:not_followed`, with both abstract states |
| a mapping with no `concrete_message/2` | `Undrivable` | `:not_followed`, named rather than an undefined function |
| a captured trace the spec permits | `Conforming` | `:ok`, 3 steps |
| a captured trace with Example 4's bug in it | `Conforming` | `:violation`, `:diverged`, at step 3 |

`:not_followed` is deliberately not a conformance failure. It says the spec permits a
behaviour the code does not take, which is a finding about the pair — one of the two is
wrong, and which one is not something the checker can decide.

## `counter` — simulation

Random walks over the real server, checked at every step. The generator draws from the
spec's own `params:`, which is where nondeterminism lives.

| Case | Verdict |
|---|---|
| 100 random traces against `Conforming` | `:ok`, 100% of the spec's actions covered |
| the same seed, twice | the same walk, state for state |
| 5 traces against `CollapsesTwoSteps` | `:violation`, and the finding is a `ExTLA.Trace` |
| that trace, handed to `ExTLA.Replay.counterexample/3` | `:diverged` again, on the same server |
| `Conforming` under the UNRESTRICTED generator | `:not_enabled` — see below |
| failure injection over 20 traces | `:ok`, with restarts, each landing in a legal state |

The unrestricted row is the interesting one. `Impl.Conforming`'s `handle_call(:done, …)`
has no guard of its own, so it accepts `:done` in a state where the spec's `done` is
disabled — and `:not_enabled` is the correct finding about that pair. It is also a finding
about nearly every server ever written, which is why the enabled-only generator is the
default and the unrestricted one is `mix extla.simulate --unrestricted`.

## What `validate!/3` does not decide

Three of §05's five rules are decidable where it runs and two are not, and the return
value says which:

- `abstract/1` returns exactly the spec's variables — needs a concrete state, so it is
  checked on every mapping by `abstract!/3` instead.
- every mapped value is a permitted state term (`02-dsl-semantics.md` §6) — same reason.
- every spec action is named by some clause — decidable only where `concrete_message/2`
  exists to enumerate them with. Without it, `ExTLA.Coverage` reports the action as never
  exercised, which is where that belongs.

Purity of `abstract/1` is not checked at all. An earlier draft of §05 said it was; it is
not decidable, and an impure mapping surfaces as a `:diverged` step. It is a documented
obligation on the author, the same shape as symmetry soundness under
`08-decisions.md` D-17.
