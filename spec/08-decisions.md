# Decision Log

Design decisions with enough rationale that they do not get re-litigated every few
weeks. Each entry records what was decided, what it replaced, and what would justify
revisiting it.

Format: **D-*n*** — short title. Superseded entries stay, marked, because the reasoning
that was rejected is part of the record.

---

## D-1 — Constants are pinned (`^name`); atoms are always literals

**Decided.** A constant is referenced as `^accounts`. A bare atom is always a literal
atom.

**Replaced:** bare atoms standing for constants (`length(:accounts)`).

**Why:** the earlier form gave one syntax two meanings that cannot be separated in
general — `status = :idle` assigns a literal, `length(:accounts)` reads a constant, and
no rule distinguishes them without knowing every declaration and every function's
intent. The pin operator already means "a value from outside this scope" in Elixir, so
it reads correctly and parses unambiguously.

**Revisit if:** a syntax emerges that is both unambiguous and lighter. Ambiguity alone
is not a trade worth making for brevity.

See `02-dsl-semantics.md` §1.1.

---

## D-2 — Action bodies are simultaneous, not sequential

**Decided.** Every RHS reads the pre-state, every LHS writes the post-state, unassigned
variables are `UNCHANGED`, and a variable may be assigned at most once.

**Why:** it is what TLA+ means, and it is the only reading under which
`x = y; y = x` swaps. The rule also makes an action body a pure function of
`(pre_state, params)`, which D-3, the symmetry canonicalization, and D-6 all depend on.

**Cost:** it surprises Elixir programmers, who read `=` as sequential rebinding. Paid
for with an explicit rule (§2), a compile error on double assignment, and `let` for the
sequential case.

See `02-dsl-semantics.md` §2.

---

## D-3 — Nondeterminism lives only in `params:`

**Decided.** `params:` is the sole branching mechanism. Entries may draw from a
constant, a literal range or list, or a function of the pre-state and the params bound
before them. `choose/2` keeps TLA+'s deterministic `CHOOSE` semantics.

**Replaced:** `choose(set)` inside an action body, documented as "explores all valid
choices".

**Why:** two reasons, either sufficient. First, the name was wrong — `CHOOSE` in TLA+ is
deterministic Hilbert choice, so giving it branching semantics would mislead everyone
who knows the notation ExTLA is modeled on. Second, it could not be implemented: a
function returning one element cannot produce several successors. Folding the state-drawn
case into `params:` removes the construct rather than fixing it, and leaves the body
deterministic.

**Revisit if:** a spec in the acceptance corpus (`07-examples.md`) cannot be expressed. The
Raft example was the hard case and it fits.

See `02-dsl-semantics.md` §3.

---

## D-4 — 64-bit fingerprints, not `phash2`

**Decided.** State identity is `:erlang.term_to_binary(state, [:deterministic])` hashed
with SHA-256, truncated to 64 bits by default. The collision estimate is reported in
every result.

**Replaced:** `:erlang.phash2`, chosen for sub-microsecond speed.

**Why:** `phash2`'s default range is 2^27-1. By the birthday bound a 10M-state run — the
stated target — would silently drop on the order of 372,000 states and report success;
even a 100K-state run loses about 37. A dropped state is an unexplored state, so the
tool would report verification over a space it never visited. That is the worst failure
mode a verification tool has, and it is not worth 1-2 microseconds per state. TLC uses
64-bit fingerprints for the same reason.

The `:deterministic` flag matters independently: plain `term_to_binary` on maps and
MapSets is not a guaranteed canonical encoding across OTP versions.

See `01-foundation.md` §`TLA.Fingerprint`.

## D-5 — The graph stores parent pointers, not states

**Decided.** Each visited state contributes `{parent, action, params}` keyed by
fingerprint. States are regenerated by forward replay when a trace is needed.

**Replaced:** `states: %{state_id => TLA.State.t()}` retained for the whole run.

**Why:** at the 10M-state target and ~1KB per state that is ~10GB of RAM, which puts the
checker out of reach of ordinary machines. The fixed record is ~64 bytes regardless of
state size, so memory scales with state count rather than state size. Trace generation
happens at most once per run and pays the replay cost instead.

**Cost:** a spec with expensive actions pays that cost twice on the failing path. The
right place for it to fall.

See `04-layer2-model-checker.md` §State Graph.

**Amended 2026-08-30.** Parent pointers form a spanning tree, which has no cycles, so
this record alone cannot support liveness checking — the original entry did not say
so, and `04` specified `sccs/1` over it. Under `check_liveness: true` the graph
additionally records each state's out-edges and one ENABLED bit per fairness
constraint, both captured while the state is materialized. States are still never
stored; per-state memory grows by ~16 bytes per edge and stays independent of state
size, which is the property this decision exists to keep. This is the split TLC makes.
See `04-layer2-model-checker.md` §State Graph, "The liveness graph".

## D-6 — Layer 3 checks step legality, not just invariants

**Decided.** After each callback, the named spec action is applied to the abstract
pre-state and its result compared to the abstract post-state. An `:unmapped` message
must leave the abstract state unchanged.

**Replaced:** computing the abstract action and then using it only for logging, while
checking invariants and action properties on the projected state.

**Why:** the replaced design is not refinement checking. Under it an implementation may
take a transition no spec action permits, and pass as long as the invariants happen to
hold — which is every interesting implementation bug. `07-examples.md` §4 is a two-line
counter whose implementation the old design would have passed and the new one rejects.

Affordable because of D-2/D-3: one function application and one comparison, cheaper than
the invariants evaluated beside it.

See `05-layer3-conformance.md` §What conformance means here.

**Amended 2026-08-30.** `check_step!/5` accepts PARTIAL params and searches the unbound
ones. An implementation routinely resolves the spec's nondeterminism itself — it pops
its own queue — so the binding is not in the message and the mapping cannot supply
it; "one application, one comparison" was only true for fully-bound actions, and
`validate!/2`'s round-trip rule was unsatisfiable for any other. A step is legal if
some binding reproduces the post-state, which is still refinement.
See `05-layer3-conformance.md` §`TLA.GenServer.Runtime`.

## D-7 — `concrete_message/2` on the refinement mapping

**Decided.** `TLA.Refinement` declares `concrete_message(action, params)`, the inverse of
`abstract_action/1`. Optional, but its absence forgoes counterexample replay and trace
validation.

**Why:** the earlier draft used it in a property-test example without ever declaring it.
It is what lets a spec-level behavior *drive* the implementation — replaying a
counterexample, or checking a captured production trace — which is the difference
between three tools that share a namespace and one pipeline.

See `05-layer3-conformance.md` §`TLA.Replay`.

## D-8 — Model checker first; Layer 1 ships with Layer 3

**Decided.** Phase 1 is the DSL, the compile-time validator and the safety checker,
accepted against a differential corpus run through TLC. Layer 1 arrives in Phase 3.

**Replaced:** Layer 1 as the MVP.

**Why:** Layer 1 de-risks nothing about Layer 2 — the layers share almost no machinery,
and Layer 1's dependencies (`TLA.State`, `TLA.Config`) are trivial. Shipping it first
would enter a market already holding Corsa, Bond, Oath and ExContract with no
differentiator, while the actually unproven part — whether this DSL can be compiled and
checked at all — stayed untested. The prior-art survey records what happens to projects
here that spend early effort on breadth.

**Revisit if:** an adopter needs Layer 1 alone and is willing to fund it. It is a small
piece once the runtime checking engine exists; it is the sequencing, not the feature,
that is being decided.

See `06-architecture.md` §Implementation Phases.

## D-9 — Differential testing against TLC is the acceptance criterion

**Decided.** The checker is accepted when it agrees with TLC on distinct state counts,
invariant verdicts and shortest-counterexample lengths across a corpus of classic specs.

**Why:** a model checker with no oracle cannot be trusted, and unit tests of a BFS loop
verify the loop, not the semantics. TLC plus the specs everyone has already written is a
free oracle, and a disagreement on state count is the most informative possible signal
that successor generation or state identity is wrong.

See `04-layer2-model-checker.md` §Differential testing against TLC.

---

## D-10 — Incomplete runs fail; coverage is reported

**Decided.** `max_states_reached` is exit code 2 and a test failure, not a warning.
Never-enabled actions and vacuously satisfied properties are reported by default and
fail under `--strict-coverage`.

**Replaced:** `IO.warn` on hitting the state limit, with the test passing.

**Why:** "we ran out of budget" is not "it holds". A suite that goes green on an
unverified spec teaches its users to believe something false, which is worse than having
no tool. The coverage report exists for the same reason one step further out: a spec
whose action is disabled by a typo'd guard verifies easily and means nothing.

See `04-layer2-model-checker.md` §Coverage and Vacuity, §ExUnit Integration.

## D-11 — Compile-time configuration, `defoverridable` wrapping

**Decided.** `TLA.Config.mode/0` is a `compile_env` macro; `:disabled` emits no wrapper
at all. Callbacks are wrapped with `defoverridable` and `super/1`.

**Replaced:** runtime `Application.get_env` with a `Mix.env()` default, and callback
renaming to `__original_handle_call__`.

**Why:** two separate bugs. `Mix` does not exist in a release, so the runtime default
raises there. And renaming breaks on multi-clause callbacks with guards — which is every
real GenServer — while `defoverridable` preserves them by construction. Compile-time
resolution is also what makes "zero production cost" true rather than approximate.

See `01-foundation.md` §Configuration, `03-layer1-invariants.md` §Compile-Time Transformation.

## D-12 — A bounded temporal fragment, stated explicitly

**Decided.** `always`, `eventually`, `~>` and state predicates, composable as given in
`02-dsl-semantics.md` §5.1. No negation, conjunction or disjunction of formulas. A
formula outside the fragment is a compile error.

**Why:** the fragment is checkable by SCC analysis without building a Büchi automaton,
and it covers what people write. The alternative failure — accepting a formula and
checking something weaker than it says — is the kind of quiet unsoundness this project
cannot afford. Widening the fragment starts with §5.1, not with the checker.

**Amended 2026-08-30.** The fragment includes `Enum.all?(^constant, fn x -> formula end)`
— quantification over a constant, which every per-process property in the corpus
needs, and which is a conjunction of in-fragment instances checked independently.
`always(P ~> Q)` is accepted as a spelling of `P ~> Q`.

## D-13 — Non-goals are written down

**Decided.** ExTLA is not a theorem prover, does not explore interleavings, does not
extract models from source, does not generate implementations, and has no real-time or
probabilistic extensions.

**Why:** the earlier specs never said what ExTLA was not, which is how a supervision-tree
DSL got designed before a working checker existed. Each non-goal has a better tool
already (TLAPS, Concuerror, Verlixir, Erla+), named in `00-prior-art.md`.

See `06-architecture.md` §Non-goals.

## D-14 — No `spec do ... end` block

**Decided.** The specification formula `Init /\ [][Next]_vars /\ Fairness` is implicit.
There is no top-level `spec` block.

**Replaced:** a `spec do init(); always(next()); fair() end` block that echoed the TLA+
formula.

**Why:** it was never given a meaning, and could not usefully have one — `Init` is the
`init` blocks, `Next` is the disjunction of declared actions, `Fairness` is the
`fairness` declarations. The block could only restate what was already declared, with
the standing risk that someone writes one that disagrees and it must then either be
ignored or mean something unspecified.

**Revisit if:** a spec genuinely needs to vary the formula — no fairness at all, or
refinement of another spec. That is a new declaration with defined semantics, added to
`02-dsl-semantics.md` before the checker.

## D-15 — Fairness is per action or per parameter binding

**Decided.** `fairness :strong, acquire_lock: [:p]` declares one constraint per binding
of the named leading params — `\A p \in P : SF_vars(AcquireLock(p))`. The bare
`fairness :weak, [:acquire_lock]` form remains and means whole-action fairness.

**Replaced:** whole-action fairness only.

**Why:** whole-action WF guarantees that *some* binding fires, which is consistent with
one process requesting forever while the others take turns. Every starvation-freedom
property in `07-examples.md` was unprovable under it. The per-binding form is what TLA+
writes, and the primer under `research/` already documented it. State-drawn params
cannot be quantified over — the set changes per state — so they are a compile error in
this position.

**Cost:** one ENABLED bit per binding per state in the liveness graph (D-5, amended).

See `02-dsl-semantics.md` §5.2.

## D-16 — Terminal states are declared with `terminal`

**Decided.** A `terminal :name do pred end` block names legitimate end states. A
successor-less state a `terminal` admits is not a deadlock; nothing else changes.

**Replaced:** `check_deadlock: false` as the only way to accept a terminating spec.

**Why:** two corpus specs terminate by design — the bounded buffer once `^max_items`
are consumed, Raft election once the term bound is exhausted — and both were reported
as deadlocks by their own acceptance tests. Turning deadlock detection off to pass them
would have hidden real deadlocks elsewhere in the same spec. TLC users add a
`Terminating` disjunct to `Next`; a declaration is the same idea without a stuttering
action showing up in coverage.

**Guard against misuse:** a `terminal` that admits a state with an enabled action is
reported by coverage as `terminal_but_live`.

See `02-dsl-semantics.md` §5.3.

## D-17 — Symmetry soundness is the author's obligation, verified dynamically

**Decided.** The compiler does not check that a `symmetry:` declaration is sound.
`--verify-symmetry` runs the model with and without the reduction on request and fails
on any disagreement.

**Replaced:** a promised compile-time rejection of order-dependent uses of a symmetric
constant.

**Why:** the promise was undecidable — a constant flows into arbitrary Elixir — and any
conservative approximation rejects the `Enum.all?(^processes, …)` every corpus spec is
built from. A verification tool that claims a check it cannot perform violates design
principle 6 more badly than one that names the obligation. The dynamic check is cheap
on a small constant assignment and catches exactly the failure the static check was
for. The *n*! canonicalization cost is now stated alongside, so the reduction is
benchmarked rather than assumed.

See `04-layer2-model-checker.md` §Symmetry.

## D-18 — Descriptions are a `desc:` option, never a positional string

**Decided.** Every declaration macro in Layers 1 and 2 takes `desc:` in its options
keyword list.

**Replaced:** `invariant(name, description \\ "", opts \\ [], do: block)` and the same
shape on `precondition`, `postcondition` and `action_property`.

**Why:** two trailing optional positionals cannot be told apart —
`invariant :x, callbacks: [...] do … end` bound the keyword list to `description`.
Layer 2's `temporal` already took `opts` while the examples passed it a heredoc, so the
two layers had drifted on the one API shape the spec said they shared.

See `03-layer1-invariants.md` §Macro Specification.

## D-19 — Type annotations are stored quoted and checked as `type_ok`

**Decided.** `type:` expressions are kept as quoted Elixir, resolved against the
constants at model-check time, and checked as an implicit invariant `:type_ok` in every
reachable state. The grammar — including `|` union, tuples and the `[d ~> r]` function
form — is written down.

**Replaced:** a `type_expr` typed as concrete values (`Range.t()`, `[term()]`) that
none of the corpus's constant-dependent types (`0..^max_val`) could have produced,
alongside `~>`/`|` type syntax used throughout the examples but specified nowhere.

**Why:** a type that mentions a constant has no value at compile time; the only honest
representation is the expression itself. Checking types as an invariant rather than
using them to prune makes a type error a reported violation rather than a silently
narrower search.

See `02-dsl-semantics.md` §1.5.

## D-20 — `f[x]` is strict function application, everywhere in a spec block

**Decided.** Inside a spec block, `f[x]` compiles to `TLA.Spec.Helpers.at/3`, which
raises `TLA.Spec.DomainError` outside the domain of `f` — for a map, for a sequence
(1-indexed, as in TLA+), and for anything that is neither. The rule has no exceptions:
it holds for a variable, a local, an `action_property`'s `old.`/`new.`, and a `params:`
generator's own state argument.

**Replaced:** `Access.get/2`, which is what `f[x]` means in ordinary Elixir.

**Why:** `Access.get/2` returns `nil` outside the domain, and `nil` is not an error.
Erlang's term order makes every comparison between types total and sorts atoms above
integers, so §8's own `require balances[from] >= amount` is **`true`** for an account
that does not exist. The guard succeeds, the action fires from a state where it was
never enabled, and the checker explores a state space the spec does not describe —
reporting success over it. That is precisely the failure `01-foundation.md` rules out
for `TLA.State.get/2`, `prime/3` and `TLA.Function.except/2`, and `[]` was the last
remaining hole in the syntax the worked example uses.

**Cost:** a keyword list indexed by its key inside a block now raises, since a list is a
sequence and `:mode` is not an index. That is the intended reading in a spec, where
state is maps and sequences.

**Why the rule has no exceptions:** the narrower version — strict on spec variables,
lax on `old.`/`new.` and on a generator's state argument — was rejected. Those are
exactly the places where a spec reaches into a collection it did not build itself, so
they are where the hole would be worth the most; and a rule an author has to remember
the shape of is one they will guess wrong.

See `02-dsl-semantics.md` §1.6 and `TLA.Spec.DomainError`.

## D-21 — Collections are element-typed with `set(t)` / `seq(t)`, and records with `%{k: t}`

**Decided.** §1.5 gains three forms: `set(t)` and `seq(t)` for a collection whose
elements are all of type `t`, and `%{k: t, …}` for a record — a map with exactly those
keys, each value of its type. Range bounds gain arithmetic (`0..(^max_items - 1)`) and
negatives (`-1..^max_ballot`).

**Replaced:** bare `:set` and `:seq`, which say nothing about what a collection holds.
They keep that meaning; the new forms are additions.

**Why:** the differential corpus found four entries typing a variable weaker than the
TLA+ they are checked against. `msgs \subseteq Message` in `two_phase_commit` and
`paxos`, `messages \subseteq Message` and `votesGranted \in [Servers -> SUBSET Servers]`
in `raft_election`, `buffer[i] \in Item` in `bounded_buffer` — all `:set` or `:seq` on
the ExTLA side. Both sides held, so no comparison was wrong; but the corpus is the
project's only oracle, and an entry that checks *less* than its oracle can agree with it
for the wrong reason. All four now check what TLC checks.

**Why a call form:** `{:set, t}` is terser and collides — it is already a legal tuple
type of the literal atom `:set` and a `t`. `[t]` collides with "one of these literals"
whenever the list has one element. `set(t)` reads like the `TLA.Spec.Helpers`
constructor of the same name and costs one grammar rule.

**Why records came too:** a set of records is what a message set is. `set(t)` with no
way to write `t` for a message would have closed the gap for `set(^servers)` and left
every message set where it was.

See `02-dsl-semantics.md` §1.5.

## D-22 — Symmetry reduction and liveness checking are refused together

**Decided.** A run that declares `symmetry:` and asks for `check_liveness: true` raises.
Safety is checked under the reduction; liveness is checked in a run without it.

**Why:** the quotient graph identifies states, so a path that leaves an orbit and a path
that returns to it look the same, and the quotient can hold cycles the real state space
does not. A cycle is precisely what a liveness verdict is read off
(`04-layer2-model-checker.md` §`TLA.ModelChecker.Liveness`), so a temporal property could
be reported as refuted by a behavior the spec does not have — or, with the fairness
constraints reading ENABLED bits of a merged state, as holding when it does not.

TLC warns about the same combination and runs anyway. A warning is not what this project
does with an unsound answer (design principle 6): the two reductions are each sound on
their own, and asking for both is asking for an answer neither of them supports.

See `04-layer2-model-checker.md` §Symmetry.

## D-23 — A temporal operator over a finite trace returns three verdicts, not a boolean

**Decided.** `TLA.Temporal`'s operators return `:holds | :violated | :inconclusive`, and
take the index a lasso's cycle returns to.

**Replaced:** `01-foundation.md` typing every operator `:: boolean()`.

**Why:** a behavior is infinite and a trace is a prefix of one. A prefix can refute `[]P`
and can satisfy `<>P`, and can do neither the other way round — P may fail after the trace
ends, or hold after it. A boolean forces "P held throughout the states I saw" to be
reported as "`[]P` holds", which is claiming more than was checked (design principle 6),
one level below where `max_states_reached` makes the same distinction.
`05-layer3-conformance.md`'s `check_temporal_properties/2` already specified these three
verdicts, so the two documents disagreed and this settles it in favor of the honest one.

A lasso removes the doubt: prefix plus repeating cycle describes an infinite behavior with
finitely many states, and every operator then answers definitely. Without one, `<>[]P`,
`[]<>P` and `P ~> Q` are `:inconclusive` for every trace.

The same section also amends `TLA.Temporal.Fairness` to take `ENABLED` as its own
argument. `ENABLED <A>_v` quantifies over every state `A` could lead to, and a behavior
holds only the states that happened, so no function of the observed steps can answer it —
the original three-argument signature was not implementable as specified.

See `01-foundation.md` §`TLA.Temporal`.

## D-24 — A state machine's state is the `{state_name, data}` pair, and its message is the event content

**Decided.** In a module instrumented through `handle_event/4`, `invariant` and
`action_property` bind `state`, `old` and `new` to the `{state_name, data}` pair, and a
`precondition` or `postcondition` pattern matches the event **content** — not
`{event_type, content}`, and not the data alone.

**Why the pair:** `:gen_statem` splits what TLA+ calls the state across two callback
arguments, and neither half is the state. A machine in `:red` with a corrupt counter is in
a bad state, and so is one whose counter is fine and whose colour is not a colour. Binding
the pair also keeps §03's `TrafficLight` — which destructures `{name, data} = state` in
the block — exactly as specified, and keeps one meaning of `state` across the behaviours.

**Why the content:** so that `precondition {:withdraw, amount}` is the same declaration
whichever behaviour carries it. The event type is OTP's transport — call, cast, info,
timeout — and a property of a specification is not about how the message arrived. A
pattern that needed to know would have to be rewritten when a call became a cast, which is
a refactoring that changes no state at all.

**Consequences:** a module defining `handle_event/4` is instrumented as a state machine
throughout, including its `init/1` (`{:ok, name, data}`, not `{:ok, state, extra}`); and
`:gen_statem`'s returns need their own extraction, because `{:stop, reason, data}` and a
GenServer's `{:stop, reason, state}` are the same shape carrying different things.
`:state_functions` mode is out of scope — its transitions are functions named after the
states, which `@on_definition` cannot recognise.

See `03-layer1-invariants.md` §What a state machine's `state` is.

## D-25 — An `Agent`'s checks are runtime-dispatched, and `:disabled` is not free for them

**Decided.** `TLA.Invariant.Agent`'s entry points are **functions**, and they ask the
declaring module at runtime whether it carries predicates. Under `mode: :disabled` a
checked `Agent` call costs one export lookup and then does what the plain `Agent` function
does — not nothing.

**Why:** everywhere else in Layer 1 the mode is resolved where the instrumented module
compiles, and `:disabled` emits no code at all. An `Agent` call site is not that place.
The transition is a function the *caller* passes in, the module whose declarations apply
is an argument, and `Application.compile_env/3` — the only way the mode is read — does not
expand inside a function body. These were macros in a first draft for exactly that reason,
and the draft does not compile.

The alternative was to leave `Agent` unsupported, which §03's §Supported OTP Behaviors
does not permit. So the cost is stated instead of hidden: an `Agent` is the one place in
Layer 1 where turning checking off leaves something behind, and it is one `function_exported?/3`
per transition, in code the author wrote explicitly rather than code a hook injected.

**Also settled here:** `callbacks:` has no meaning for an `Agent`. It restricts a
declaration to named OTP callbacks and the caller's function is not one — it runs inside
`Agent`'s own `handle_call/3`. Every declaration in the named module applies to every
checked transition.

See `03-layer1-invariants.md` §An `Agent`'s checks cannot be compiled away.

## D-26 — §6's term check runs at discovery, inside the state graph

**Decided.** `TLA.State.validate!/1` is called by `TLA.StateGraph.add_state/5`, on the
branch where the state's fingerprint is absent from the table — so once per **distinct**
state. The caller does not validate, and the successor is registered *before* its action
properties are evaluated.

**Replaced:** validation in `TLA.ModelChecker.take_action/6`, on every generated
successor. On `TLA.Differential.RaftElection` at the corpus constants that was 255,270
validations where 58,359 would do, and 77.9% of a 23.4 s search.

**Why it is sound, which is the part worth recording.** Validating only new states
necessarily happens *after* the state has been hashed, since newness is knowable only from
the fingerprint — so the ordering §6 appears to demand (validate before you fingerprint)
is not achievable. It is also not the ordering that matters. What matters is that
validation precedes any *use* of the state, and the guarantee survives for a reason
specific to the terms §6 rejects: a pid, reference, port, fun or float is precisely a term
whose encoding does not recur. A state carrying one therefore cannot dedup against an
earlier state, always misses the table, and is always validated on the path that reaches
it first. `:erlang.term_to_binary/2` encodes such terms without complaint, so reaching the
check is guaranteed rather than lucky.

**Why the graph and not the checker.** §6 exists *for* fingerprinting — the terms it
forbids are exactly those whose encoding does not identify a state. Putting the check
where the fingerprint is taken keeps the rule beside its reason, and lets every caller
assume that a state which has entered the graph is one the checker has vetted.

**What this forced.** `add_state/5` now runs before `Safety.check_action_properties/5`
rather than after. Left in the old order, a user's action property would be handed a state
§6 had not yet rejected, and a forbidden term would surface from inside that predicate
instead of from a diagnostic naming the variable — a worse error about a different thing.
The hoist also collapsed two `add_state/5` call sites into one.

**Measured:** 2.65x on `raft` (25.2 s to 9.5 s) and 1.62x on `buffer`, interleaved on one
machine, minima compared. Validation itself fell 4.47x against the 4.37x that the
transition-to-state ratio predicts.

**Revisit if:** a term is ever added to §6's permitted set whose encoding *can* recur
while still being forbidden. The soundness argument above depends on the forbidden terms
being exactly the non-recurring ones, and would have to be rebuilt.
