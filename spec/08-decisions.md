# Decision Log

Design decisions with enough rationale that they do not get re-litigated every few
weeks. Each entry records what was decided, what it replaced, and what would justify
revisiting it.

Format: **D-*n*** — short title. Superseded entries stay, marked, because the reasoning
that was rejected is part of the record.

---

## D-1 — Constants are pinned (`^name`); atoms are always literals

**Decided.** A constant is referenced as `^accounts`. A bare atom is always a literal
atom.

**Replaced:** bare atoms standing for constants (`length(:accounts)`).

**Why:** the earlier form gave one syntax two meanings that cannot be separated in
general — `status = :idle` assigns a literal, `length(:accounts)` reads a constant, and
no rule distinguishes them without knowing every declaration and every function's
intent. The pin operator already means "a value from outside this scope" in Elixir, so
it reads correctly and parses unambiguously.

**Revisit if:** a syntax emerges that is both unambiguous and lighter. Ambiguity alone
is not a trade worth making for brevity.

See `02-dsl-semantics.md` §1.1.

---

## D-2 — Action bodies are simultaneous, not sequential

**Decided.** Every RHS reads the pre-state, every LHS writes the post-state, unassigned
variables are `UNCHANGED`, and a variable may be assigned at most once.

**Why:** it is what TLA+ means, and it is the only reading under which
`x = y; y = x` swaps. The rule also makes an action body a pure function of
`(pre_state, params)`, which D-3, the symmetry canonicalization, and D-6 all depend on.

**Cost:** it surprises Elixir programmers, who read `=` as sequential rebinding. Paid
for with an explicit rule (§2), a compile error on double assignment, and `let` for the
sequential case.

See `02-dsl-semantics.md` §2.

---

## D-3 — Nondeterminism lives only in `params:`

**Decided.** `params:` is the sole branching mechanism. Entries may draw from a
constant, a literal range or list, or a function of the pre-state and the params bound
before them. `choose/2` keeps TLA+'s deterministic `CHOOSE` semantics.

**Replaced:** `choose(set)` inside an action body, documented as "explores all valid
choices".

**Why:** two reasons, either sufficient. First, the name was wrong — `CHOOSE` in TLA+ is
deterministic Hilbert choice, so giving it branching semantics would mislead everyone
who knows the notation ExTLA is modeled on. Second, it could not be implemented: a
function returning one element cannot produce several successors. Folding the state-drawn
case into `params:` removes the construct rather than fixing it, and leaves the body
deterministic.

**Revisit if:** a spec in the acceptance corpus (`07-examples.md`) cannot be expressed. The
Raft example was the hard case and it fits.

See `02-dsl-semantics.md` §3.

## D-4 — 64-bit fingerprints, not `phash2`

**Decided.** State identity is `:erlang.term_to_binary(state, [:deterministic])` hashed
with SHA-256, truncated to 64 bits by default. The collision estimate is reported in
every result.

**Replaced:** `:erlang.phash2`, chosen for sub-microsecond speed.

**Why:** `phash2`'s default range is 2^27-1. By the birthday bound a 10M-state run — the
stated target — would silently drop on the order of 372,000 states and report success;
even a 100K-state run loses about 37. A dropped state is an unexplored state, so the
tool would report verification over a space it never visited. That is the worst failure
mode a verification tool has, and it is not worth 1-2 microseconds per state. TLC uses
64-bit fingerprints for the same reason.

The `:deterministic` flag matters independently: plain `term_to_binary` on maps and
MapSets is not a guaranteed canonical encoding across OTP versions.

See `01-foundation.md` §`TLA.Fingerprint`.

## D-5 — The graph stores parent pointers, not states

**Decided.** Each visited state contributes `{parent, action, params}` keyed by
fingerprint. States are regenerated by forward replay when a trace is needed.

**Replaced:** `states: %{state_id => TLA.State.t()}` retained for the whole run.

**Why:** at the 10M-state target and ~1KB per state that is ~10GB of RAM, which puts the
checker out of reach of ordinary machines. The fixed record is ~64 bytes regardless of
state size, so memory scales with state count rather than state size. Trace generation
happens at most once per run and pays the replay cost instead.

**Cost:** a spec with expensive actions pays that cost twice on the failing path. The
right place for it to fall.

See `04-layer2-model-checker.md` §State Graph.

## D-6 — Layer 3 checks step legality, not just invariants

**Decided.** After each callback, the named spec action is applied to the abstract
pre-state and its result compared to the abstract post-state. An `:unmapped` message
must leave the abstract state unchanged.

**Replaced:** computing the abstract action and then using it only for logging, while
checking invariants and action properties on the projected state.

**Why:** the replaced design is not refinement checking. Under it an implementation may
take a transition no spec action permits, and pass as long as the invariants happen to
hold — which is every interesting implementation bug. `07-examples.md` §4 is a two-line
counter whose implementation the old design would have passed and the new one rejects.

Affordable because of D-2/D-3: one function application and one comparison, cheaper than
the invariants evaluated beside it.

See `05-layer3-conformance.md` §What conformance means here.

## D-7 — `concrete_message/2` on the refinement mapping

**Decided.** `TLA.Refinement` declares `concrete_message(action, params)`, the inverse of
`abstract_action/1`. Optional, but its absence forgoes counterexample replay and trace
validation.

**Why:** the earlier draft used it in a property-test example without ever declaring it.
It is what lets a spec-level behavior *drive* the implementation — replaying a
counterexample, or checking a captured production trace — which is the difference
between three tools that share a namespace and one pipeline.

See `05-layer3-conformance.md` §`TLA.Replay`.

## D-8 — Model checker first; Layer 1 ships with Layer 3

**Decided.** Phase 1 is the DSL, the compile-time validator and the safety checker,
accepted against a differential corpus run through TLC. Layer 1 arrives in Phase 3.

**Replaced:** Layer 1 as the MVP.

**Why:** Layer 1 de-risks nothing about Layer 2 — the layers share almost no machinery,
and Layer 1's dependencies (`TLA.State`, `TLA.Config`) are trivial. Shipping it first
would enter a market already holding Corsa, Bond, Oath and ExContract with no
differentiator, while the actually unproven part — whether this DSL can be compiled and
checked at all — stayed untested. The prior-art survey records what happens to projects
here that spend early effort on breadth.

**Revisit if:** an adopter needs Layer 1 alone and is willing to fund it. It is a small
piece once the runtime checking engine exists; it is the sequencing, not the feature,
that is being decided.

See `06-architecture.md` §Implementation Phases.

## D-9 — Differential testing against TLC is the acceptance criterion

**Decided.** The checker is accepted when it agrees with TLC on distinct state counts,
invariant verdicts and shortest-counterexample lengths across a corpus of classic specs.

**Why:** a model checker with no oracle cannot be trusted, and unit tests of a BFS loop
verify the loop, not the semantics. TLC plus the specs everyone has already written is a
free oracle, and a disagreement on state count is the most informative possible signal
that successor generation or state identity is wrong.

See `04-layer2-model-checker.md` §Differential testing against TLC.

---

## D-10 — Incomplete runs fail; coverage is reported

**Decided.** `max_states_reached` is exit code 2 and a test failure, not a warning.
Never-enabled actions and vacuously satisfied properties are reported by default and
fail under `--strict-coverage`.

**Replaced:** `IO.warn` on hitting the state limit, with the test passing.

**Why:** "we ran out of budget" is not "it holds". A suite that goes green on an
unverified spec teaches its users to believe something false, which is worse than having
no tool. The coverage report exists for the same reason one step further out: a spec
whose action is disabled by a typo'd guard verifies easily and means nothing.

See `04-layer2-model-checker.md` §Coverage and Vacuity, §ExUnit Integration.

---

## D-11 — Compile-time configuration, `defoverridable` wrapping

**Decided.** `TLA.Config.mode/0` is a `compile_env` macro; `:disabled` emits no wrapper
at all. Callbacks are wrapped with `defoverridable` and `super/1`.

**Replaced:** runtime `Application.get_env` with a `Mix.env()` default, and callback
renaming to `__original_handle_call__`.

**Why:** two separate bugs. `Mix` does not exist in a release, so the runtime default
raises there. And renaming breaks on multi-clause callbacks with guards — which is every
real GenServer — while `defoverridable` preserves them by construction. Compile-time
resolution is also what makes "zero production cost" true rather than approximate.

See `01-foundation.md` §Configuration, `03-layer1-invariants.md` §Compile-Time Transformation.

---

## D-12 — A bounded temporal fragment, stated explicitly

**Decided.** `always`, `eventually`, `~>` and state predicates, composable as given in
`02-dsl-semantics.md` §5.1. No negation, conjunction or disjunction of formulas. A
formula outside the fragment is a compile error.

**Why:** the fragment is checkable by SCC analysis without building a Büchi automaton,
and it covers what people write. The alternative failure — accepting a formula and
checking something weaker than it says — is the kind of quiet unsoundness this project
cannot afford. Widening the fragment starts with §5.1, not with the checker.

## D-13 — Non-goals are written down

**Decided.** ExTLA is not a theorem prover, does not explore interleavings, does not
extract models from source, does not generate implementations, and has no real-time or
probabilistic extensions.

**Why:** the earlier specs never said what ExTLA was not, which is how a supervision-tree
DSL got designed before a working checker existed. Each non-goal has a better tool
already (TLAPS, Concuerror, Verlixir, Erla+), named in `00-prior-art.md`.

See `06-architecture.md` §Non-goals.

---

## D-14 — No `spec do ... end` block

**Decided.** The specification formula `Init /\ [][Next]_vars /\ Fairness` is implicit.
There is no top-level `spec` block.

**Replaced:** a `spec do init(); always(next()); fair() end` block that echoed the TLA+
formula.

**Why:** it was never given a meaning, and could not usefully have one — `Init` is the
`init` blocks, `Next` is the disjunction of declared actions, `Fairness` is the
`fairness` declarations. The block could only restate what was already declared, with
the standing risk that someone writes one that disagrees and it must then either be
ignored or mean something unspecified.

**Revisit if:** a spec genuinely needs to vary the formula — no fairness at all, or
refinement of another spec. That is a new declaration with defined semantics, added to
`02-dsl-semantics.md` before the checker.
