> **Closed 2026-09-02.** Delivered by #64, #65, #66 and #67 under the milestone *The
> verification ledger*: `TLA_COVERAGE.md` with a HARD drift gate, per-item content versions,
> the `spec_version:` stamp, and a pinned JSON schema for `mix tla.check`. Section (c) — the
> extraction of the generic golden machinery into a shared leaf library — was resolved by
> `surfex` (`dco-tek/surfex`), which ExTLA now consumes as a `only: [:dev, :test]` dependency,
> so consumers inherit nothing.

## Problem

ExTLA verifies *behavior*. Nothing in it answers the question one layer out:

> **Which parts of my specification are actually covered by verification, is that
> coverage current, and does the implementation still claim to refine the version of
> the spec that was checked?**

Three concrete failure modes the current design cannot detect:

1. **A stale verdict.** `mix tla.check` passes on Monday. On Tuesday someone edits an
   action's guard. The spec is now unverified, and nothing says so. TLC has this
   problem too — it has no notion of "the spec changed since this result".
2. **A silently invalidated refinement mapping.** `Refinement.abstract/1` is written
   against a set of spec variables. A variable is renamed or an action's post-state
   changes; `abstract_action/1` still compiles and still returns an action name. The
   mapping is now wrong in a way that only shows up as `:diverged` at runtime, if the
   path is ever exercised.
3. **Coverage that exists only in scrollback.** `TLA.Coverage` (specified in
   `04-layer2-model-checker.md`) reports never-enabled actions and vacuous properties to a
   terminal. Nobody reads a terminal from three weeks ago, and CI does not diff it.

## Prior art: agentronic's surface goldens

`agentronic` solved a structurally identical problem — keeping spec, code, and API
surface aligned — and its convention is written up as `§Conv.2` in
`agentronic/spec/conventions-02-surface-goldens.md`. Ten goldens are in production
(`SPEC_COVERAGE.md`, `AUTHZ_SURFACE.md`, `NODE_INTERFACE.md`, and others). The
mechanism:

| Element | What it does |
|---|---|
| **Self-cataloging surface** | The declaration IS the catalogued fact, so the golden can neither list a fact nothing declares nor omit one something does |
| **Generated, never hand-edited** | `mix <task> --write`; a pure function of source (no boot, no clock, no VCS data) |
| **HARD drift gate** | CI re-scans and byte-compares; a golden that no longer matches the code FAILS. The document cannot lie |
| **Content version per row** | 8 hex of sha256 over the item's *normalized* definition (AST position metadata stripped), so a row changes only when its item's definition changes — not when something above it moves |
| **Evidence ladder** | `static_gate` ▸ `property` ▸ `sim_invariant` ▸ `integration_test` ▸ `unit_test` ▸ `prose_citation` ▸ **NOTHING**; the NOTHING list is the verification backlog |
| **Freshness stamps** | `@validates ["Cat.N.M@<version>"]`; when the section's body hash moves, the stamp goes **STALE** and must be re-confirmed |
| **One shared renderer** | `Maatronic.SourceScan.Golden` (240 lines, pure) — "the renderer IS the convention", so per-file dialects cannot form |

Current state there: 1110 sections, 914 normative, 300 tagged validations, **0 stale**.
The `VALIDATION_SURFACE.md` variant is the closest analogue to ExTLA's need — it
*inverts* the direction, projecting a surface the **spec** declares and asking what the
code has built.

## Assessment

The pattern is a good fit, but it is **three separable things**, and only one of them
belongs inside ExTLA.

### (a) BELONGS IN ExTLA — `TLA_COVERAGE.md`, a drift-gated verification golden

ExTLA already accumulates every declaration it needs (`@tla_variables`, `@tla_actions`,
`@tla_invariants`, `@tla_temporals`) and already must compute `TLA.Coverage`. Writing
that to a committed, drift-gated file is a small delta over work already specified — and
it adds the one thing neither ExTLA nor TLC currently has: **a verification result is a
claim about a specific version of a spec, and a content hash makes staleness
detectable.**

Proposed `mix tla.coverage --write` → `TLA_COVERAGE.md`, one row per spec item:

```
# TLA_COVERAGE.md
Every item each TLA.Spec declares, its content version, the strongest verification
that covers it, and whether that verification is current.
Generated by `mix tla.coverage --write` · gate `tla-coverage-drift` (HARD) — do not
edit; a drift FAILS the gate.

Evidence, strongest→weakest: `model_checked` ▸ `refinement_checked` ▸ `simulated`
▸ `property` ▸ `unit_test` ▸ **NOTHING**.
Freshness: `fresh` (stamp == current version) · **STALE** · `unstamped` · `—`

**4 specs · 31 items** · model_checked 22 · refinement_checked 6 · nothing 3 · gap = 3
**Freshness** · fresh 28 · stale 3 · unstamped 0

## Specs.TransferProtocol — 12 items · gap 0 · stale 1

| Item | Kind | Version | Evidence | Fresh | Exercised | Locus |
|---|---|---|---|---|---|---|
| `begin_transfer` | action | `a1b2c3d4` | `model_checked` | `fresh` | 3,612 states | `spec/transfer.ex` |
| `complete_transfer` | action | `5e6f7a8b` | `model_checked` | **STALE** | 3,612 states | `spec/transfer.ex` |
| `cancel_transfer` | action | `9c0d1e2f` | **NOTHING** | — | **never enabled** | `spec/transfer.ex` |
| `conservation_of_money` | invariant | `3a4b5c6d` | `model_checked` | `fresh` | 802 near-miss | `spec/transfer.ex` |
| `type_ok` | invariant | `7e8f9a0b` | `model_checked` | `fresh` | **0 near-miss** | `spec/transfer.ex` |
| `error_recovery` | temporal | `1c2d3e4f` | `model_checked` | `fresh` | **VACUOUS** | `spec/transfer.ex` |
```

The `Exercised` column is what makes this ExTLA's golden rather than a generic one: it
carries the vacuity and never-enabled findings that only a model checker can produce,
in a form CI diffs and a human reads three weeks later.

### (b) BELONGS IN ExTLA — the `@refines` version stamp

Agentronic's `@validates ["Cat.N.M@<version>"]` applied to refinement mappings, which is
exactly where ExTLA needs it (failure mode 2 above):

```elixir
use TLA.GenServer,
  spec: Specs.TransferProtocol,
  spec_version: "a1b2c3d4"        # compile error if the spec's hash has moved
```

The mapping author is then forced to re-confirm when the spec changes, instead of
discovering it as a runtime `:diverged` on a path that may not be exercised for months.
This closes a real hole in `05-layer3-conformance.md` that the current spec does not
address at all.

### (c) DOES NOT BELONG IN ExTLA — the golden machinery itself

The reflect → render → content-hash → byte-compare → gate mechanism is **not
TLA-specific**. Bundling it into ExTLA would make every ExTLA user inherit a
documentation-generation framework they did not ask for, and would couple a
verification library to a docs convention.

It is also *already shaped for extraction*: `maatronic/source_scan` declares `deps: []`,
stdlib only, explicitly so any member can depend on it, and
`Maatronic.SourceScan.Golden` is a 240-line pure renderer. Per CLAUDE.md's "make tooling
as project agnostic as possible", the right move is a **separate leaf library** that
both agentronic and ExTLA depend on — not a copy in each.

That extraction is agentronic's call, not ExTLA's. Per the Cross-Project Boundary Rule
it needs a proposal filed there (`/prop-cross-project agentronic`), not an edit from
here. **Not filed yet — awaiting approval.**

### (d) ALSO WORTH DOING — ExTLA as an evidence producer for agentronic

Agentronic's ladder tops out at `static_gate`. ExTLA produces evidence strictly stronger
than anything on it: exhaustive verification over a bounded model, and machine-checked
refinement of an implementation against a spec. Two new classes at the top:

```
model_checked ▸ refinement_checked ▸ static_gate ▸ property ▸ sim_invariant
  ▸ integration_test ▸ unit_test ▸ prose_citation ▸ NOTHING
```

ExTLA already specifies `--format json` output (`04-layer2-model-checker.md` §Mix
Integration), so this needs only a **stable JSON result schema** on ExTLA's side and a
reader on agentronic's. Cheap, and it makes both projects better without merging them.

## Scope

**In scope for this proposal (ExTLA only):**

1. `TLA.Coverage.Golden` — render the existing `TLA.Coverage.t()` plus spec content
   versions to `TLA_COVERAGE.md`, following `§Conv.2`'s notation (header block, stats
   line grammar, typed cells, content version column, **no timestamps**).
2. `mix tla.coverage [--write]` and a `tla-coverage-drift` CI gate.
3. `TLA.Spec.version/1` — the content hash of a spec item's normalized definition, AST
   position metadata stripped. Reuses `TLA.Fingerprint`'s canonical encoding.
4. `spec_version:` on `use TLA.GenServer`, checked at compile time.
5. A stable JSON schema for `mix tla.check --format json`, so (d) is possible.

**Explicitly out of scope:**

- The generic golden renderer (see (c)) — belongs in a shared leaf library.
- A general evidence ladder over unit tests, integration tests and prose. ExTLA knows
  only about evidence ExTLA produces; it should be a *producer* into someone else's
  ladder, never own the general one.
- `mix surface.report` equivalent. One golden does not need a cross-surface aggregator.

## Sequencing

This is deliberately **not** a Phase 1 item in full, because the previous scope review
(`spec/08-decisions.md` D-8) concluded that breadth before a working checker is how
projects in this space die. Split accordingly:

| Item | Phase | Rationale |
|---|---|---|
| 3 (`TLA.Spec.version/1`) | 1 | Needed by everything else; reuses `TLA.Fingerprint`; ~a day |
| 1, 2 (golden + gate) | 1, minimal | `TLA.Coverage` is already Phase 1; writing it to a gated file is a small delta and is what stops coverage findings from evaporating |
| 5 (JSON schema) | 1 | Already specified as an output format; only the schema needs pinning |
| 4 (`spec_version:`) | 3 | Ships with Layer 3, since it stamps refinement mappings |
| (c), (d) | — | Not ExTLA work. (c) is a cross-project proposal; (d) follows from 5 |

## Open questions

1. **Hash granularity.** Per spec item (action, invariant, temporal) or per spec module?
   Per item is agentronic's answer and the reason its goldens auto-merge in parallel
   worktrees (CLAUDE.md, golden-conflict protocol). Recommend per item.
2. **Is the drift gate HARD from day one?** Recommend yes. An advisory gate on a
   verification artifact is the same mistake as `IO.warn` on `max_states_reached`
   (D-10).
3. **Does `TLA_COVERAGE.md` live at the project root** (agentronic's convention) or under
   `spec/`? Root, for the same reason agentronic puts them there: it is a status
   artifact, not a specification.

## Relationship to existing decisions

- Extends D-10 ("incomplete runs fail; coverage is reported") from a terminal report to
  a durable, CI-gated artifact.
- Fills a gap in D-6/D-7 (Layer 3 refinement checking): the mapping is checked at
  runtime, but nothing today notices when the *spec it was written against* moves.
- Constrained by D-8 (checker first): the sequencing above keeps Phase 1 to the parts
  that are a small delta on already-planned work.
